## 最適化が必要な理由（実装前の観測）

現在の構成はモデル共通のルール検索・指示文であり、確認した実行経路にAstra固有設定やAPI呼び出しはない。モデル名の置換による移行は不要。Astraでの比較評価はまだ行っておらず、「Astraに最適」とは判断できない。

| 観測した箇所 | 現状と影響 | 対応案 |
|---|---|---|
| `scripts/query-rules.ts:15` | 既定100件の詳細JSON。実測282,631 bytes / 271,980文字 | 少数の検索結果とID指定詳細取得を分ける |
| 同`:17` | 日本語だけのtaskは検索語が0件になり、task条件が無効になる | 日本語statementも検索。未対応入力を無条件検索へ変換しない |
| 同`:19`、`src/lib/store.ts:23` | ID順で絞り込み後に切り詰める。重要性・関連度による順序ではない | 適用範囲を先に確認し、競合優先順位・platform具体性・関連度で決定的に整列 |
| 同`:30` | 件数上限のみ。総一致数、省略表示、出力量上限がない | preflight、総件数、省略件数、続き取得、bytes上限を追加 |
| 同`:33` | Markdownは条件・例外・scope・confidence等を省略 | 判断に必要な情報を残したcompact形式を追加 |
| `scripts/build-adapters.ts:47` | `--task review` はレビュー処理指定に見えるが、実際は英語の文字列検索 | 実在するフィルターと検索意図が一致する例へ変更 |

全JSONは10,434,601 bytes。全体を会話へ読み込まない。3,664ルールにconditions、248ルールにexceptionsがあるため、単純な短文化による条件の脱落を避ける。以上のbytes・文字数はAstraの実測トークン数ではない。

[OpenAIのAstra公式ガイド](https://developers.openai.com/api/docs/guides/latest-model)は、AGENTS.md等の指示監査、曖昧な指示の解消、委任量と検証範囲の調整を勧めている。このリポジトリでは検索契約と生成指示文の明確化に適用する。APIのキャッシュ設定やモデルパラメーター追加は、現状の構成には適用しない。

## 実行順序と完了条件

| 工程 | 作業範囲 | 完了条件 |
|---|---|---|
| 1. 取得量を制御 | queryの件数・bytes事前集計、少数のcompact結果、ID詳細取得、日本語入力、明示的な省略情報。generator経由でCodex指示文を更新 | canonical rule内容・IDが不変。条件・例外・出典の欠落なし。必須CI成功 |
| 2. 小規模な比較評価 | 12件の固定検索ケースをローカル評価。必要なら3タスクだけ旧/新のAstra動作を比較 | 重要ルールの取りこぼし増加0、出典解決100%、同じ必要情報で取得payloadを50%以上削減する目標。未達なら拡大せず原因を限定 |
| 3. HIG差分の試行レビュー | 当日の変更候補から、accessibility/privacyと規範強度を優先して最大3ページまたは50ルール | ハッシュ変更と意味変更を区別。根拠URL・section・取得時刻・hash、19語以下の証拠、判断・未解決事項を保存 |
| 4. 残りを分割反映 | 試行実測に基づいてページ単位で見積もり直し、残りを少量ずつ処理 | source-review等のsource traceを再照合。ID維持、削除はdeprecated。生成後CI成功。blocked・未レビューを明示 |

工程1はモデルへの入力を制御する仕組みを先に作るもの。工程3以降で更新候補を内容まで評価する。`npm run sync` は発見・取得・抽出を全件実行するため、最初の試行には使わない。ページ単位の取り込みが現行CLIでできない場合は、隔離コピーでの差分抽出／対象限定機能を最初に用意する必要がある。

source-review、normative-review、duplicate-reviewはハッシュや候補集合に結び付くため、古い判断へ新しいhashだけを付け替えない。本文変更でも規則の意味が不変なら、その確認根拠を記録した上でレビューを更新する。

固定検索ケースにはiOS/iPadOS/macOS/tvOS/visionOS/watchOS/CarPlay、accessibility/privacy、keyboard、権限拒否・offline、日本語、0件、条件・例外を含める。件数を増やす前に小標本の結果を報告する。検証項目はケース間で兼用できる。

## 消費を抑える運用と事前告知

**正確な総トークン上限は、この環境の利用枠表示からは設定・保証できない。** 履歴の再送、推論、ツール出力、補助エージェントも消費へ影響する。モデルのcontext windowとアカウント利用枠は別物。API料金からCodex残量を逆算しない。

次回着手時の小規模試行を次の条件で運用する。

- 同時作業は主担当＋独立した補助1名まで。補助には全会話・全ルールを渡さず、限定した対象と短い報告形式を渡す。
- 検索はまず10件。compact応答は12,000 bytes、詳細は1回32,000 bytesを仮の上限とする。超過時は規則の途中を切らず、次ページへ分割し省略を明記する。
- 原文はプログラム内で解析し、会話には必要なsectionだけを取得。原文全文をファイルへ永続化しない。ログはファイルへ送り、会話には結果集計だけ返す。
- 1回のsource reviewは最大3ページまたは50ルール。長いページではsection単位へさらに分割する。
- CIは変更まとまりごとに1回。新たな変更・失敗・未解決事項がなければ反復しない。
- 各工程の開始・終了と長い工程の中間で利用枠を確認。試行開始から**使用率が5ポイント以上増加**、または**残量が30%以下**なら、次のbatchを開始せずcheckpointと再見積もりを報告する。共有枠・表示の粒度や遅延があるため、厳密な停止上限ではない。
- checkpointには対象URL、完了rule ID、未解決理由、次のコマンド、検証結果を保存する。次回はそこから再開する。利用枠のresetはこの計画の前提にしない。

bytes上限は再現可能な出力量制御であり、token上限ではない。例えばASCII主体の文字列を4文字/tokenと仮定すると、現状の既定出力だけで約68,000 tokens相当になるが、日本語・JSONの分割次第で変動するため予算値に流用しない。

工程1〜2は小規模試行として着手し、工程3の最大3ページを終えた時点で、実際の変更ページ数と観測消費率から残りを再見積もりする。**全件レビューの固定見積もりは試行前に約束しない。** 意味変更が少なければ対象を減らし、多ければ複数回へ分ける。

今回の975件をすべて再レビューする場合、50件上限だけでも最低20batchになる。これは全件実行を勧める見積もりではなく、先に意味変更のあるsectionへ絞る必要性を示す規模の目安。最初の3ページは件数の小さいページだけに偏らず、規範上の優先度と条件の複雑さも考慮して選ぶ。

着手前の告知には「今回の工程、対象ページ/ルール数、出力上限、利用枠開始値、終了条件」を含める。この計画は自動実行や定期実行の予約ではない。

## 未検証・注意点

- ページhash差分は本文文字列の変更検出であり、ルールの意味変更数ではない。
- 現行check-updatesの出力にはページ別の旧/新hash値が含まれない。今回の監査記録はbaseline inventoryと差分ファイルのhashを保存した。source review開始時には、その時点のcopyright-safe inventoryとsection traceも保存して根拠を更新する。
- 現行check-updatesはblockedを差分と別集計するが、取得失敗時のnull hashや探索漏れが変更/削除候補へ混ざり得る。blockedがある場合は先に解消し、削除を確定しない。
- 全ナビゲーションの探索やselectorの完全性、画像・動画・複雑な表の意味まで保証した監査ではない。
- 「low-confidence 0」「review_required 0」は旧source snapshotに対する状態。当日の公式HIGを確認済みという意味ではない。
- 変更する場合はcanonical storeとgeneratorから再生成し、生成済みAGENTS.md等を手編集しない。
